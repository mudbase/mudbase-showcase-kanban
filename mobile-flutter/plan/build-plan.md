# Build Plan — Mudbase Showcase: Kanban (Flutter)
Generated: 2026-08-01
Mode: port (Flutter reimplementation of the Next.js reference app in `../web`)
Type: mobile (fullstack via BaaS, no custom backend)
Stack: Flutter + Dart, Riverpod (plain `Notifier`/`AsyncNotifier`, no codegen), go_router,
`flutter_secure_storage`, `socket_io_client`, talking directly to `cloud.mudbase.dev` through the
real, generated Mudbase Dart SDK (`mudbase_sdk`).

## Stack Decisions
- Mirrors the sibling `mudbase-showcase-social`/`mudbase-showcase-ecommerce` Flutter apps'
  architecture (verified by reading `mudbase-showcase-social/mobile-flutter/lib/core/*`,
  `features/auth/auth_controller.dart`, `router/app_router.dart`, `theme/app_theme.dart` before
  writing a line of this app) — same `AuthService`/`MudbaseDataService` raw-`dio` pattern, same
  `SecureTokenStorage`, same `AsyncNotifier`-based `AuthController` with `callAuthorized`/
  401-refresh-retry, same plain Riverpod (no `riverpod_generator`/`freezed`), for the same reason:
  no Flutter SDK is installed in this build environment, so nothing generated by `build_runner`
  could be iteratively verified locally — every provider and model here is verifiable by
  `dart analyze` alone.
- **No registration screen.** The task brief reuses three already-registered, already-verified
  demo accounts (`kanban.owner.demo@gmail.com` / `.member.` / `.viewer.`, all
  `KanbanTest123!`) and explicitly forbids registering new ones. `AuthService` therefore has no
  `registerWithRole` method at all (unlike the sibling ports) — an unused signup method would be
  genuine dead code here, not a documented-but-idle API surface, since this app ships no
  `RegisterScreen` and no path ever calls it.
- **Card/list movement: button/menu-based, not drag-and-drop** — mirrors the reference web app's
  own deliberate choice (`web/plan/build-plan.md` "Stack Decisions"). Each card gets an up/down
  reorder pair and a "Move to…" `PopupMenuButton` (the natural touch-UI equivalent of the web's
  `<Select>` dropdown); each list gets left/right reorder arrows. Every move still writes
  `position`/`listId` and appends an `activity` row exactly as the web app's data model specifies,
  regardless of which UI triggered it.
- **One `BoardController` for lists+cards combined**, not two separate controllers. The reference
  web app's `useLists`/`useCards` are two independent TanStack Query hooks that `BoardView.tsx`
  composes and groups client-side (`useMemo`). A Flutter screen needs one `AsyncValue` to build
  against, so `BoardState` (in `lib/features/board/board_controller.dart`) holds both lists and
  cards as one snapshot with `sortedLists`/`cardsByListId` getters doing the same grouping
  `BoardView.tsx`'s `useMemo` does. `ActivityFeedController` stays separate (own screen, own
  realtime subscription — see "Realtime" below).
- **Every mutation refetches the whole board rather than patching a local cache by hand.** Same
  strategy as the reference web app (`invalidateQueries` after every mutation) and the sibling
  ports' realtime handling: at demo scale (a handful of lists/cards) a full refetch is
  effectively instant, and it is far less failure-prone than replicating a differently-shaped
  local-cache patch for six different mutation kinds (create/rename/reorder/delete list,
  create/edit/delete/move/reorder card).

## Real-Project Verification (done live against cloud.mudbase.dev before writing UI code)

Read `../web/plan/build-plan.md`, `../web/src/lib/mudbase.ts`, and every hook under
`../web/src/hooks/` in full before writing any Dart. That document already contains two
significant live-verified platform findings this port depends on and does **not** re-derive from
scratch:

1. **`boardId`/`assigneeId` are ObjectId-typed, not free strings.** The `boards` collection
   (`6a6d405cd07caabbbdfc5c79`) already exists with one document,
   `6a6d4072d07caabbbdfc5d3c` — that is the real `BOARD_ID` this app's `EnvConfig.boardId`
   defaults to. `assigneeId` is derived from the typed assignee name via `pseudoObjectId()`
   (`lib/core/formatters.dart`) — a djb2-hash-based, deterministic, always-24-hex-char id — ported
   bit-for-bit from the web app's `src/lib/utils.ts` (see that file's inline comment for exactly
   how Dart's `int.toSigned(32)`/`int.toUnsigned(32)` reproduce JS's `ToInt32`/`>>> 0` semantics).
2. **Clearing an assignee requires `null`, never `""`.** `CardRepository.update` always sends
   `assigneeId`/`assigneeName` as `null` when the caller passes no assignee name — an empty string
   is rejected the same way an invalid ObjectId format would be.

This build additionally re-confirmed, live, against the exact same project (see "Live Smoke Test
Results" below): all three demo accounts authenticate with the correct `customRole`; the seeded
board already had lists/cards from the reference web app's own smoke test; a member's raw
`ListRepository.create` call is rejected `403`; a viewer's raw `CardRepository.create`/`update`/
`delete` calls are all rejected `403`; `POST /api/auth/refresh` returns a distinct new token pair;
an invalid bearer token is rejected `401`.

## Auth Model (matches the reference web app's, adapted for a mobile app with no anonymous session)

This app has no anonymous/guest session and no public read — every one of the three roles
(`owner`/`member`/`viewer`) requires a real login, same real platform behavior the web app
documents (every Mudbase collection permission here requires authentication). `AuthController`
(`lib/features/auth/auth_controller.dart`) only attempts `getSession()` when a token already
exists in `SecureTokenStorage`; there is no anonymous-session bootstrap to skip. The router's
`redirect` (`lib/router/app_router.dart`) sends every screen except `/login` back to `/login` once
the auth state resolves to no session — mirroring the web app's `AuthGate`.

`LoginScreen` ships three "Owner / Member / Viewer" quick-fill buttons (mirroring the web app's
`LoginForm` "Sign in as…" buttons) alongside a normal email+password form, using exactly the three
demo accounts named in the task brief. There is no `RegisterScreen` — see "Stack Decisions" above.

## RBAC Matrix (enforced server-side by Mudbase's own collection permissions; UI mirrors it for defense-in-depth)

| Action | owner | member | viewer |
|---|---|---|---|
| Read lists | ✅ | ✅ | ✅ |
| Create/rename/delete/reorder lists | ✅ | ❌ | ❌ |
| Read cards | ✅ | ✅ | ✅ |
| Create/edit/delete/move cards | ✅ | ✅ | ❌ |
| Read activity | ✅ | ✅ | ✅ |
| Create activity (implicit, via card/list writes) | ✅ | ✅ | ❌ |

`lib/core/rbac.dart` is a direct Dart port of the web app's `src/lib/rbac.ts`
(`canManageLists`/`canManageCards`/`isReadOnly`/`roleLabel`/`isAppRole`) — client-side UX gating
only, not the security boundary. `BoardScreen` hides list-restructuring controls from `member` and
all write controls from `viewer`, showing a small "Read-only — you're signed in as Viewer" banner
instead (matching the web app's exact wording). See "Live smoke test results" below for the raw
API write attempts proving the server enforces this independently of any UI.

## Data Models (Mudbase Collections — already provisioned, used as-is, not recreated)

Identical schema to the web app (`../web/plan/build-plan.md` "Data Models") — every `boardId`
field everywhere is the constant `6a6d4072d07caabbbdfc5d3c`.

### lists — `6a6d29cad07caabbbdfc3f9a` (`lib/models/board_list.dart`)
`boardId`, `name`, `position`. Fetched `sort: "position"` for column order.

### cards — `6a6d29cad07caabbbdfc3fad` (`lib/models/board_card.dart`)
`boardId`, `listId`, `title`, `description?`, `position`, `assigneeId?`, `assigneeName?`,
`createdById`, `createdByName`. Fetched once per board (`filter: { boardId }`, `sort: "position"`)
and grouped client-side by `listId` (`BoardState.cardsByListId`), same as the web app.

### activity — `6a6d29cbd07caabbbdfc3fc6` (`lib/models/activity_entry.dart`)
`boardId`, `actorId`, `actorName`, `action`, `cardTitle?`, `fromList?`, `toList?`. `action` is
modeled as a Dart `enum` (`ActivityAction`, six known cases + `unknown` for forward
compatibility) rather than a raw string, per this project's Dart pattern rules (sealed/enum types
with exhaustive `switch`) — `lib/core/activity_text.dart`'s `describeActivity()` is a direct port
of the web app's `src/lib/activity-text.ts`, including the same `unknown`/`default` defensive
fallback sentence. Fetched `sort: "-createdAt"` for the reverse-chronological feed.

## Auth Flow
```
Cold start, no token in secure storage  → AuthController.build() resolves to null → router
                                           redirects to /login (no anonymous/guest session)
Login                                    → POST /api/auth/local/login { email, password,
                                             projectId } → 200 + token/refreshToken +
                                             user.customRole ("owner"/"member"/"viewer")
401 on any authenticated call            → AuthController.callAuthorized refreshes once (deduped
                                             via _refreshInFlight, since refresh tokens are
                                             single-use/rotating) → retries the original request
                                             once → rethrows if that also fails, tearing the
                                             session down locally
Logout                                   → POST /api/auth/logout (best-effort revoke) → local
                                             session always cleared regardless, socket disconnected
```

## Realtime
`BoardController` subscribes to the `lists` and `cards` collections' Socket.IO rooms
(`subscribe:collection` → `db:create`/`db:update`/`db:delete`, same contract as the web app's
`useBoardLive`) and calls its own `refresh()` (a full board refetch) on any matching event — so
another signed-in user's column add/rename/delete/reorder or card create/edit/move/delete appears
live for every other viewer/member without a manual refresh. `ActivityFeedController` subscribes
independently to just the `activity` collection for the Activity tab — a deliberate simplification
from the web app's `useBoardLive` (which the web app calls from both the board page and the
activity page, subscribing all three collections either way): since this app's two screens are
separate routes with separate controllers, each only needs to stay live for what it actually
renders. Behavior is identical from the user's perspective — both the board and the activity feed
update live — this only changes which controller owns which subscription.

## UI Screens
- `/login` — email+password form plus three "Owner / Member / Viewer" quick-fill buttons
  (`lib/features/auth/login_screen.dart`).
- `/board` (default tab) — the board: app bar (title, role badge, sign-out), a horizontally
  scrollable row of `ListColumn`s (each with its `CardTile`s and, for owners, rename/delete/reorder
  controls), an owner-only floating "Add list" button, a read-only banner for viewers
  (`lib/features/board/`).
- `/activity` (second tab) — full reverse-chronological activity feed, updating live, pull-to-
  refresh (`lib/features/activity/`).

Both screens share one bottom-nav shell (`lib/features/shell/home_shell.dart`,
`StatefulShellRoute.indexedStack`) — mirroring the sibling ports' two/three-tab shells, adapted to
this app's two screens (no separate "Account" tab; sign-out lives in the board app bar since it is
the app's home screen).

## Security Implementation
- Input validation: form field length caps matching the web app (`Input`/`TextFormField`
  `maxLength`) — card titles 120 chars, descriptions 2000, assignee names 80, list names 60.
- Authentication: Mudbase-issued JWT (access + refresh) held in `flutter_secure_storage`
  (Keychain/EncryptedSharedPreferences) — **never** `SharedPreferences` (hard project security
  rule, same as every sibling Flutter port), with 401 → refresh → retry handled once, deduped
  across concurrent calls (`AuthController._refreshInFlight`).
- Authorization: enforced server-side by Mudbase's own collection permissions per the RBAC matrix
  above — this app's own role checks (`lib/core/rbac.dart`) are UX gating (hide/disable controls),
  not the security boundary. Verified live for both `member` (list-create) and `viewer` (card
  create/update/delete) — see "Live smoke test results" below.
- Secrets: none. Every value in `lib/config/env_config.dart` (project id, three collection ids,
  board id, base URL) is public, exactly like the web app's `NEXT_PUBLIC_*` vars — there is no
  server-side credential anywhere in this app.

**Note on the auth rate limit encountered mid-build**: this project's `/api/auth/local/login`
endpoint is rate-limited to 5 requests / 15 minutes per IP (documented in
`.claude/skills/on-demand/baas-integration/SKILL.md` §26) — a hard platform control, not a bug.
This same shared demo project is exercised by every language/platform port's own smoke test (10
ports total, per the repo root README), so the login budget was already spent by other ports'
concurrent test runs by the time this port's own first attempt ran. The fix was to stop retrying
immediately (each retry itself consumes another slot in the 15-minute sliding window, so hammering
it only prolongs the block) and instead let a full quiet cooldown period elapse before the single
retry captured above, which passed cleanly on the first attempt after the wait.

## Known Limitations (real platform constraints, not bugs — inherited from the web app)
- **No `users` collection.** Assignee/creator/actor display names are denormalized onto the row
  that references them (`assigneeName`, `createdByName`, `actorName`) at write time, rather than
  looked up from a central users table.
- **Same-list reorder uses a two-write position swap**, not a fractional-index scheme — correct
  and simple at demo scale (a handful of cards per column), same documented tradeoff as the web
  app.
- **Login is rate-limited (5/15 min per IP)**, shared across every port exercising this same demo
  project — see the smoke-test note above.
